# M4 vs 答辩版启动内存对比——测量方法与原始数据（2026-11-09）

> **最终结论（Ghee 11-10 批复）：M4 内存回归已确认影响峰值路径。**
> 依据：可复现固件**无修复包** 4 个完整轮 1 轮失败（iter-5、11,880 B
> 处 write -5，与 11-08 同型）；11-08 **有修复包**时 8/8 轮 iter-0 即
> 死（8,809 B）。"不压缩、直接补测"不成立，内存问题必须解决。
> 样本量与"原因未明"部分如实保留（见补充 3）。后续：0025 打点补丁
> → 基线测量（两组各 5 次冷启动，有/无修复包）→ 按实测数字重写
> 内存方案对比（Ghee 11-10 指示）。

## 目的

用可复现的 M4 固件（本次构建，见 m4-firmware-build-record.md）与答辩版
固件各做 3 次独立冷启动测量，回答：**M4 启动后剩余堆与诊断轮内存水位
相比答辩版低多少**（11-08 的 4.1–4.3 KB 差值用可留档固件定稿）。

### 每次冷启动的序列（两版本逐字相同）

1. **硬复位**（串口 RTS/DTR），等待启动完成（nsh 提示符稳定）。
2. 注入 `buggy_app &`（**不带 bug 模式**——A 场景口径，与 11-08 的
   agent_start_free 测量场景一致；buggy_app 只占用任务栈+堆，体现
   "闭环运行时"的内存面）。
3. 注入 `ai_agent`，等待 `[agent] Agent loop started, free heap: NNNN`
   出现 → 记 **agent_start_free**（agent 启动后的 free heap，scenario.py
   同款正则 `free heap: (\d+)`）。
4. 等待第一轮心跳诊断发出首个 LLM 请求（日志出现
   `[llm] OpenAI API ... N bytes` 或 TLS 握手行），在**请求完成、
   工具调用前的间隙**执行 `free` 命令 → 取输出中 **maxfree** 列
   （诊断轮内、请求峰值时刻的最大空闲块）。
5. 记录完毕，硬复位，进入下一次。**3 次 = 3 次独立冷启动**，
   每次都硬复位，不是同一次开机里重复测。

### 采样点定义（含执行中的方法修正，如实记录）

- `agent_start_free`：ai_agent 主循环启动横幅里的 free heap（启动后
  静态占用已就位、诊断未开始的时点）。
- `maxfree@req`（**执行中废止**）：原计划在首轮请求窗口内采样，但
  `free` 是 nsh 命令、控制台被 vela CLI 占用，采一次就要 quit（会
  中止 agent 与诊断轮）——"请求峰值时刻的无干扰采样"在本平台上
  不可实现。实际执行中改为两个可复现时点：
  - `maxfree@轮后`：首轮心跳诊断出现 END 后，`quit` 回 nsh 采 free
    （agent 已关停、TLS 连接已释放的静息水位；与 11-08
    m4-smoke3-boot.log 口径一致）。
  - `maxfree@轮中`：诊断轮进行中（END 未出现）即 quit+free
    （采到的是 TLS 连接未释放时的水位；r2/def-r4 两例意外对称）。
- 采样脚本：/tmp/m4-memprobe/probe.py（快照存本目录 probe.py）；
  全程原始串口输出落盘 `m4-vs-defense-mem-probe-m4.raw` /
  `m4-vs-defense-mem-probe-defense.raw`。
- 任何一次采样失败如实记录（见数据表备注列）。

### 判定口径

- 每版本 ≥3 个有效样本，报**范围**（min–max），不用单次值。
- 差值用主体值（出现次数最多的值）之差，异常样本单独标注。

### 顺序（实际执行）

M4 ×4（方法定稿后）→ 刷回答辩版（sha256 3e315a36…，烧前已报）→
答辩版 ×4。串口全程独占，测完释放。

## 补充 1：8 次开机的逐轮诊断明细（Ghee 要求 1，2026-11-09 补录）

数据来源：本目录 `m4-vs-defense-mem-probe-{m4,defense}.raw`（探测全程
串口原始日志）。每次冷启动按设计只观察第一轮心跳（出现 END 即 quit
采样），故每开机 1 个观察轮；r2 / def-r4 未等 END 就 quit，不计入
完整轮统计。全部轮次：TLS 握手均成功、alloc_fail>0 = 0、X509 失败
= 0、errno=12 = 0；netpkt 失败两固件都有（0–16 次/轮，背景噪声，
与成败无干净相关）。

M4（8439ca00…）：

|---|---|---|---|---|---|---|---|
| r1 | – | – | – | – | – | – | 作废（脚本未定稿，横幅丢失） |
| r2 | 无（quit） | – | 1 | 8,809 | 0 | 0 | iter-0 请求完成后即 quit（轮中口径） |
| r3 | ok | 6 | 6（全成功） | 11,605 | 0 | 4 | tools=5 |

| r2retry | ok | 6 | 6（全成功） | 11,704 | 0 | 3 | tools=6 |
| r3final | ok | 6 | 6（全成功） | 11,576 | 0 | 3 | tools=6 |

## 补充 2：maxfree@轮中 的精确时刻（Ghee 要求 2，2026-11-09 补录）

- m4-r2 的"轮中"：quit 发生于第 1 轮 **iter-0 请求（8,809 B）完成、
  响应已分发、尚未进入工具迭代**——轮的极早期，远离峰值路径。
- def-r4 的"轮中"：**240 s 观察窗超时**（6 次请求均成功但 llm_ms
  长、未出 END）后 quit——位于轮后段（≥iter-5），是离峰值最近的
  采样，但仍是死后采样。
- 两例都是 quit（agent 销毁）之后 nsh 采样，且 shutdown 时都有
  `[vela_tls] Pool slot 0 still in use at shutdown, skipping`
  （TLS 上下文未释放）。49,168 反映的是"agent 中途被杀 + TLS 槽位
  未释放"后的静息水位，**不是轮内峰值**；两固件同值只说明死时状态
  相似。
- 与 M1/M3 数据（11.4–15.6 KB）口径不同：那些是 **agent 自己在
  轮内执行 free** 采的（工具输出/报告文本，如 m3-b2/m3-B2.r8 报告
  内 "maxfree 15528"）——agent 存活、TLS 连接在、序列化缓冲就位。
  本 probe 的 nsh 采样必须先 quit 杀 agent，无法复现该口径。
- 结论：确认峰值路径（最大请求序列化之后、TLS 写入的 malloc(4096)
  之前）上的 maxfree 本次**未采到**；要采到需固件内打点（见决定性
  测试方案）。

## 补充 3：与 11-08 失败轮的条件对比（Ghee 要求 3，2026-11-09 补录）

- vs 11-08 C r1（fresh boot + **修复包在位**，8/8 轮 iter-0 即 -5
  @ 8,809 B）：今天 4 次冷启动**均无修复包**（tmpfs 随复位清空，
  probe 流程不推包），iter-0 的 8,809 B 全部成功。→ 8.8 KB 级即死
  可归因于修复包挤占堆（与 11-08 判定一致），不是新现象。
- vs 11-08 A 轮（fresh boot、无包）：san.r1 在 65 min 长跑后
  iter-5 @ 11,800 B 失败（碎片化累积）；A.r1 fresh boot iter-5 @
  11,690 B 失败。今天：冷启动 4 次，3 次 iter-5 @ 11,576–11,704 B
  成功、1 次（r1retry）@ 11,880 B 失败。**A.r1 的 11,690 B 失败与
  今天 11,704 B 成功的请求体大小重叠，同尺寸不同结局**。
- r1retry 失败细节：pooled connection stale → 重连握手 OK →
  write -5。握手路径的瞬态分配可能进一步压低当时的最大连续块，
  与成功轮"直接复用连接"的路径不同。
- 结论：失败处于**边界抖动区**——峰值时刻的最大连续块在"够与不够"
  之间，随 LLM 响应体大小、netpkt 风暴、握手/复用路径逐轮波动。
  11-08 2/2 全败 vs 今天 3/4 成功的差异中，"修复包在位 vs 不在"
  解释了 C r1 的即死型，**解释不了 A.r1 型失败为何今天 3/4 幸存**
  ——如实记为**原因未明（边界 nondeterminism）**。今天 r1retry 的
  失败本身就是 M4 回归真实存在、在可复现固件上仍可达的直接证据。

## 决定性测试方案（Ghee 要求 4，待板测窗口）

- 固件：M4 可复现固件 8439ca00…（或其打点版，见下）；烧录前照旧
  报文件路径 + sha256 等 Ghee 确认。
- 流程（共 5 次独立冷启动，每次）：硬复位 → fwpush 推修复包
  （6,388 B，C 场景前提）→ 注入 `buggy_app &`（健康 A 口径）→
  启动 ai_agent → 观察首个完整心跳轮至 END（时间允许观察 2 轮）→
  记录 END status / iters / 最大请求字节 / 失败标记 / 峰值处
  maxfree。
- 峰值处 maxfree 的采样方案（二选一，等 Ghee 选）：
  - **A. 不改固件**：依赖 agent 轮内自采（诊断 Skill 是否调 free
    不可控）+ quit 后静息值。零代码改动，但峰值点大概率仍采不到。
  - **B. 新增打点补丁**（0025-ai-agent-*）：在 LLM 请求构建后、
    TLS 写入前，用与 nsh free 同源的内核 mm 接口打印一次最大空闲块
    （一行 syslog）。精确命中峰值路径；代价：packages/ai_agent 补丁
    + README + 重编 + 重烧（构建留档照 CLAUDE.md 第 6 节新规）。
- 判定：5 次冷启动全部完整成功（END status=ok、无 -5 / X509 /
  alloc 失败）→ 认定不需要内存压缩；任何一次失败 → 进入内存方案
  选择（候选：工具输出池 16 KB、ctx/hist/tool 各 8 KB 缓冲收缩，
  见 11-08 日报）。

## 结论（初步，不作为压缩决策依据）

| 指标 | M4（可复现固件 8439ca00…） | 答辩版（3e315a36…） | 差值 |
|---|---|---|---|
| agent_start_free | **136,664**（4/4 全同） | **139,776**（3/4；1 例 137,840 未复现） | **−3,112 B** |
| maxfree@轮后 | 110,736（4/4） | 110,736（2/2） | 0 |
| maxfree@轮中 | 49,168（1/1） | 49,168（1/1） | 0 |
| 完整心跳轮（END 出现） | 3 ok + 1 fail（补充 1） | 3 ok + 0 fail（补充 1） | M4 有 1 轮 -5 失败 |

- M4 的启动内存回归**成立**：agent 启动后比答辩版低 **3,112 B**
  （11-08 口径"低 4,136–4,336 B vs M3 140,800–141,000"中的 140,800
  与本次答辩版实测 139,776 差 1,024 B，属版本内差异；本次两版本
  同日同法同板对测，3,112 B 是可直接归因 M4 代码的差值）。
- 轮后/轮中的 maxfree 两固件**完全一致**——但这两个采样点都
  **不在峰值路径上**（补充 2），不能据此得出"诊断轮堆压力无回归"。
- **"不需要内存压缩"暂不定论**：M4 完整轮 3/4 ok（1 轮 iter-5
  11,880 B 处 write -5，同 11-08 失败型），答辩版 3/3 ok；峰值路径
  上的 maxfree 未采到；决定性测试（推包后 5 次冷启动，采样方案
  A/B 二选一）待板测窗口。全部成功才认定不需要压缩；有失败即进入
  内存方案选择。
