## 一、L3 热修复的设计思路

### 1.1 在闭环里的位置

恢复阶梯（补丁 0017，tool_recover.c）目前到 L2 为止：

| 级 | 动作 | 现状 |
| --- | --- | --- |
| L1 | SIGUSR1 软恢复（唤醒消费者） | ✅ 已实现（stall 场景一次到位） |
| L2 | SIGTERM + 按 mode 文件重启同一 workload | ✅ 已实现（0020 起支持内建名回退） |
| **L3** | **加载 /data/patches/ 下修复版 ELF 替换故障任务** | 本文设计，赛后实现 |
| 收尾 | L3 仍失败 → needs_human，人工介入前不再自动处置 | ✅ 已实现 |

L3 的触发条件不变：L1、L2 后复采样仍 Δ=0（或复现观察期内复发），
阶梯升到 L3。LLM 仍只"提议"，L3 的加载、复核、升级判定全部在
recover_task 的 C 代码里完成（设计规则 3.2）。

### 1.2 修复版 ELF 长什么样

以场景 C 暴露的真实缺陷为例（2026-11-04，m3-C.r1）：
buggy_app 的 bug 模式在**消费者排水路径上少一次计数释放**
（`g_count -= g_bug ? 0 : 1`），生产者永久死等。修复版就是把这一行
改回无条件递减——**一处改动、单文件**。这决定了修复版 ELF 的整体
形态：

- 源码同 buggy_app（app/hello_app/buggy_app_main.c），单编译目标
  `buggy_app_fixed`，`-Os`、裁剪调试段，估算 text ≤3KB、
  文件 ≤8KB（实测原版 text 692B / 文件 4900B，M2 改造加 1–2KB）。
- 修复版**只在开发阶段预构建**，烧进 /data/patches/ 等待加载；
  运行时绝不生成或编译代码（红线 8）。
- 修复版进程名与白名单：0008 白名单已预留"buggy_app（及热修复后的
  修复版进程）"，L3 加载后 verify_pid_target 按进程名前缀
  buggy_app 族匹配，不需要新白名单。

### 1.3 加载与执行机制

elf 示例已验证的路径（architecture-notes 假设 2，代码级已证实）：

```c
exec(filename, args, NULL, g_elf_exports, g_elf_nexports);
```

- `g_elf_exports`（34 符号：printf / pthread_* / usleep / sigaction /
  kill / task_create …）覆盖 buggy_fixed 全部外部依赖；
  L3 复用同一张表（或从 elf 示例链接同一份 symtab）。
- **执行入口**：elf 示例在独立任务里调 exec()（exec 语义是替换当前
  映像，不能在 ai_agent 自己的任务里直接调）。L3 先 task_create 一个
  轻量 loader 任务，loader 里 exec 修复版 ELF——修复版进程从此顶着
  loader 的任务槽继续跑，等价于"带修复的任务重启"。
- 不能用 PSRAM 放代码段：0013 只放开了 PMP entry 6 与 9（内部 SRAM
  堆区）的执行权限。ELF 运行镜像必须落在内部 SRAM。
- 重定位后的指令缓存同步由 0014 保证（exec 路径已含 icache sync）。

### 1.4 阶梯与复核（不变）

```
L1 SIGUSR1 → 3s → 复采样 Δ=0
L2 SIGTERM + spawn → 6s → 复采样 Δ=0
L3 停任务 → loader exec 修复版 → 6s → 复采样 Δ>0
   → 复现观察 120s → 再次 Δ>0 → {"result":"recovered","level":3}
   → 任一步 Δ=0 → 升级 needs_human
```

判定行（0019 的单行 JSON）扩展 `"action":"hotfix"`，
result 取值不变；actions.log 与 report.md 六段式不变。

## 二、内存账：修复版 ELF vs 当前最大空闲块

### 2.1 需求侧（加载全流程峰值）

| 项 | 估算 | 说明 |
| --- | --- | --- |
| 修复版文件本体 | ≤8KB | tmpfs 驻内存（SMARTFS 方案下读入缓冲另计） |
| 运行镜像（text+data+bss） | ≤4KB | 重定位后驻留，直到热修复进程退出 |
| 加载器瞬态 | 几 KB | 按段读取 + 重定位表，逐段释放 |
| **合计峰值** | **≤15KB** | 发生在处置阶段，不在诊断序列化窗口内 |

### 2.2 供给侧（各阶段 maxfree 实测）

| 数据集 | 固件 | maxfree（B） |
| --- | --- | --- |
| m0 v5 批量 | 基线 | 28,000–44,000 |
| m1-b45 / m1-50round | B1–B5 | 36,424–47,464 |
| m1-b6c-validate | B6 | 18,736 |
| M2 板上验收（11-03） | 0015–0017 | 11,400–15,600 |
| M3 B×10（11-04 白天） | 0015–0019 | 10,040–15,528（r1/r8 采样） |

### 2.3 对比结论（如实口径）

- 以 11-03 空间评估的最差观测 18.7KB 对 ≤15KB 预算，**余量约 3.7KB**；
  但 M2/M3 以来诊断期间的 maxfree 降到 **10.0–15.6KB**，与 15KB 预算
  **基本持平、局部低于预算**——这是 M4 的首要风险（见第四节）。
- 缓解的事实基础：这两个口径都是**诊断进行中**的瞬时值；热修复动作
  发生在诊断完成后的处置阶段，此刻不再持有请求序列化的活动状态，
  maxfree 实测普遍比回归表内数值高 3–5KB。
- 底线口径不变：M2/M3 共 50+ 轮 OOM=0、校验器拦截=0，静态 16KB
  请求缓冲（0016）消除了 12.5KB 级单次分配。

### 2.4 预算不足时的备选（按优先级）

1. **错峰加载**：L3 前显式释放本轮诊断的动态上下文（记忆/工具输出
   缓冲），再加载——不动架构，收益 2–4KB。
2. **瘦身修复版**：`-Os` + 单段 + strip，目标文件 ≤5KB、镜像 ≤3KB。
3. **文件缓冲搬 PSRAM**：只把"文件字节"放 PSRAM，代码段仍锁内部
   SRAM（PMP 不变）——需要先写 ESP32-P4 第二堆 bringup
   （假设 1：可行但非开关活，风险中等）。
4. 真不够就砍 L3 的"同时驻留"假设：修复版先加载、原任务先停，
   保证任一时刻只有一个 buggy 镜像在内存。

## 三、/data 重启清空：解决方案选项

事实（architecture-notes 2026-11-02）：`agent_main.c:496` 把 /data
挂成 tmpfs，**修复版 ELF 放 /data/patches/ 活不过重启**，热修复
"断电后仍生效"的故事立不住。选项（blockers 2026-11-02 条目展开）：

| 选项 | 做法 | 优点 | 代价 / 风险 |
| --- | --- | --- | --- |
| A. SMARTFS 全盘持久化 | /data 换 SPI flash 16MB SMARTFS 分区（config 已有支持） | 一劳永逸；report / actions.log 也断电可查 | 挂载点冲突需评估；**磨损**：agent 每 120s 写报告+审计，日写 ~1500 次，无磨损均衡时寿命存疑 |
| B. 维持 tmpfs + 开机串口推包 | 每次上电脚本把修复版 ELF 推进 /data/patches/ | 零内核改动；HIL 已能做 | "热修复重启仍在"叙事弱化为"现场重推"；人工步骤进演示流程 |
| **C. 混合：只持久 /data/patches** | 独立小 SMARTFS 分区挂 /data/patches，其余（日志/证据）留 tmpfs | 修复包断电保留；**日志高频写不进 flash，磨损面只剩低频写入的修复包** | 需两次挂载与分区脚本；掉电一致性（写包中途断电）要测 |
| D. 修复版固化进固件镜像 | 编译期链接进 nuttx.bin | 最稳 | 不再是"热修复"，违背 M4 命题，仅作兜底 |

**推荐 C**：磨损面最小、叙事完整、内核改动局限在挂载代码。
A 作赛后长期方案（与 blockers 的 SMARTFS 决定一致）。
11-03 的决定是"赛后按 SMARTFS 方案落地持久化后补 M4"，即 C 或 A
二选一在赛后实施。

## 四、风险清单

| # | 风险 | 等级 | 应对 |
| --- | --- | --- | --- |
| 1 | **maxfree 预算持平**（10–15.6KB vs ≤15KB 估算） | 高 | 二节 2.4 的四级缓解；实现前先在处置阶段实测 maxfree |
| 2 | /data 持久化未落地，修复包重启即丢 | 高（叙事） | 选项 C；未落地前 M4 验收明确按"不掉电"口径 |
| 3 | exec()/posix_spawn 对重定位 ELF 的 API 差异（openvela vs 上游） | 中 | 0014 已证明 exec 路径可用（elf 七项全过）；按 elf 示例原样复刻 loader 任务 |
| 4 | 修复版进程的任务名/身份文件与 verify_pid_target 不匹配 | 中 | 加载后复用 publish_identity；verify 按前缀 buggy_app 族匹配（0017 已如此） |
| 5 | 加载器或修复版泄漏（对照 ai_agent 关停泄漏 TLS 池的先例） | 中 | elf 测试的 Memory Usage Change: 0 口径；L3 后必须复核 free |
| 6 | 修复版符号表缺符号（未来修复需要新 API） | 低 | g_elf_exports 可扩；缺符号在加载期报错即拒绝执行 → 升级人工 |
| 7 | SMARTFS 磨损 / 挂载冲突 | 中 | 选项 C 缩小磨损面；掉电写包测试列入验收 |
| 8 | PMP：误把代码放 PSRAM 导致取指异常 | 低 | 镜像分配走内部 SRAM 堆；跑 buggy_app pmp 子命令复核 |

## 五、预计工作量（赛后排期）

| 阶段 | 内容 | 估时 |
| --- | --- | --- |
| 1. 持久化 | 选项 C：分区 + 双挂载 + 掉电测试（或 A 全盘 + 磨损评估） | 1–2 天 |
| 2. 修复版构建流 | Makefile 目标 buggy_app_fixed、strip、symtab 导出 | 0.5–1 天 |
| 3. L3 rung | loader 任务 + exec、白名单/身份、判定行扩展（补丁 0021+） | 1–2 天 |
| 4. 板上回归 | 场景 C 全链（L1 无效 → L2 复现 → L3 恢复）、内存收支归零、判定行逐轮核对 | 1–2 天 |
| 合计 | | **约 5–8 个工作日** |

验收建议（沿用 M2/M3 口径）：C 场景 5 轮 L3 恢复率 ≥90%；
场景 A 误处置保持 0；L3 轮前后 maxfree 收支不劣化；OOM 与
校验器拦截保持 0（底线不破例）。
