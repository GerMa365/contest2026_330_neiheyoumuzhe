# 后续工作路线图（2026-11-04）

> 决赛交付后的持续演进方向。按**更强 / 更稳 / 更好用**三类组织，
> 每项给出：要解决的问题、思路、依赖关系、预计工作量。
> M4 的详细设计（内存账、/data 方案、风险）见
> [docs/m4-design.md](m4-design.md)，本文只作简述与排期引用。

**已知局限（2026-11-04，M3 场景 C 实测）**：长会话末段堆水位降至
~19KB free 时，收尾写报告的 LLM 调用可能因分配失败而丢失
（8KB 响应缓冲 / 4KB 请求头缓冲，静默失败；C 5/5、B 1/10，
机制分析见 docs/evidence/2026-11-04/m3-acceptance.md）。**关键
审计记录不受影响**：判定行与 actions.log 由 C 代码确定性写入
（串口 + 文件），先于失败落盘；缺失的只是 LLM 撰写的叙述性
报告。对应本路线图第二项（PSRAM 扩容）与第五项（离线降级的
报告补写），修复面在内存侧。

## 一、更强（能力扩展）

### 1. M4：L3 ELF 热修复

- **问题**：L2 只能"重启同一份代码"；如果故障在代码本身
  （如场景 C 的排水路径缺陷），重启只会复现，最终只能升级给人。
- **思路**：阶梯补上 L3——停掉故障任务，由 loader 任务 exec
  /data/patches/ 下预构建的修复版 ELF（复用 elf 示例的
  g_elf_exports 符号表），复采样确认恢复后按 recovered 收尾。
  修复版只在开发阶段构建（红线：运行时不生成/编译代码）。
- **依赖**：/data 持久化（修复包断电保留，见第八项）；ELF 加载
  的两层修复（0013 PMP / 0014 icache）已就位；内存预算紧张时
  依赖 PSRAM 兜底（见第二项）。
- **工作量**：**5–8 人日**（设计已冻结在 m4-design.md）。

### 2. 启用 PSRAM 第二堆

- **问题**：404KB 堆是全项目硬约束，诊断期 maxfree 已降到
  10.0–15.6KB；M4 的修复版加载预算（≤15KB 峰值）与之持平，
  后续功能（黑匣子、网页报告）也都要内存。
- **思路**：ESP32-P4 板级代码目前没有 PSRAM 堆注册——需自写
  esp-hal PSRAM 初始化 + mm_addregion 第二堆。注意：**代码段
  仍必须落内部 SRAM**（0013 只放开 PMP entry 6/9 的执行权限），
  PSRAM 只放数据、文件缓冲等非执行内容。
- **依赖**：与 M4 的关系是"兜底而非前置"——M4 先按内部 SRAM
  实现（错峰加载 / 瘦身修复版），板上实测预算不够时才上 PSRAM
  （m4-design 2.4 的第 3 级缓解）。反之 PSRAM 也不等 M4，可
  独立为后续功能扩容。参考配置 `configs/psram_usrheap` 存在但
  是 xtensa 系的，P4 需要自己 bringup。
- **工作量**：**2–3 人日**（bringup + 注册 + 回归）。

### 3. 通用心跳接口（让其他程序接入监控）

- **问题**：心跳判据（计数文件约定）是 buggy_app 专属，别的
  程序想被"卡死检测"覆盖时没有接入方式。
- **思路**：把心跳协议化——约定计数文件路径/命名与语义
  （单调递增、写入即推进），可选注册接口让程序自报心跳地址；
  诊断 Skill 泛化为"按目标采样心跳"，recover_task 白名单按
  目标扩展（仍保持白名单收口，不做通用 kill）。
- **依赖**：无硬依赖；改 Skill 文本（skill_loader.c 与 skills/
  双份同步）与判据常量。
- **工作量**：**2–3 人日**。

## 二、更稳（可靠性）

### 4. 看门狗预警中断 + 黑匣子记录

- **问题**：Agent 自身卡死 / 堆耗尽时没有现场可查；复位后
  "上一次发生了什么"随 RAM 一起消失，诊断无从谈起。
- **思路**：软狗在硬看门狗超时前 N 秒先触发预警中断，ISR 把
  关键现场（最后 N 条日志、free/maxfree、任务表、心跳计数）写进
  黑匣子（保留 RAM 区优先，其次 /data 文件）；重启后诊断第一步
  先读黑匣子，向 LLM 与报告（六段式加一节"上次现场"）汇报。
- **依赖**：黑匣子落文件时依赖 /data 持久化（第八项）；保留 RAM
  需确认 P4 的 LP RAM 复位行为。与"离线降级"共用现场数据。
- **工作量**：**3–5 人日**。

### 5. 离线降级模式（LLM 不可达时规则先行）

- **问题**：LLM 不可达时整个闭环瘫痪——夜间 B 有 7/10 轮
  net_llm，故障既发现不了也处置不了。
- **思路**：确定性预案——C 代码规则表先行：心跳 Δ=0 持续 N 个
  周期即不经 LLM 直接走 recover_task 的既有守卫/阶梯（stall →
  L1/L2），动作限于已验证的最小集；LLM 恢复后 Agent 复核现场并
  补写报告。等价于"预案自动执行，事后补记录"。
- **依赖**：0017 的守卫/阶梯本就是确定性代码，本项只是把"提议
  者"从 LLM 换成规则；需要 Kconfig 模式扩展（off/dry-run/
  confirm/auto 之外加 rules 档或独立开关）。
- **工作量**：**3–4 人日**。

### 6. 热修复程序签名校验

- **问题**：L3 加载修复版 ELF 等于执行外来代码；修复包被篡改
  （存储污染 / 供应链）就是任意代码执行。
- **思路**：构建期对修复版签名（ed25519，公钥编进固件），L3
  加载前验签，失败即拒绝执行并升级人工——与 0008 工具白名单
  同属"执行面收口"。mbedTLS 既有依赖，签名原语现成。
- **依赖**：M4（保护对象是 L3 本身），可与 M4 同期实现。
- **工作量**：**2–3 人日**。

## 三、更好用（产品化）

### 7. 报告推送通知（飞书 / 钉钉 webhook）

- **问题**：报告只落板上文件，人不主动连串口就不知道出事或恢复。
- **思路**：报告写完后 HTTP POST 一行摘要（判定 + 三行结论）到
  webhook；网络不可达时排队重试、上限丢弃，不影响主诊断流。
- **依赖**：网络栈与 TLS 连接池已有（0011 调过）；注意堆预算，
  复用现有连接而不是新建大户。
- **工作量**：**1–2 人日**。

### 8. 报告持久化到 Flash（SmartFS）

- **问题**：/data 是 tmpfs，报告与 actions.log 掉电即失——证据
  链只能靠串口镜像。
- **思路**：与 m4-design 第三节同一方案——推荐**混合挂载**：
  只把 /data/patches（或再加 evidence）挂到 SPI flash 的
  SmartFS 分区，高频日志留 tmpfs 控制磨损；掉电一致性与磨损
  评估列入验收。
- **依赖**：SmartFS 配置已在 config 里；与第四、第一项共享此
  存储底座。
- **工作量**：**1–2 人日**（含掉电测试）。

### 9. 网页查看报告（webpanel）

- **问题**：看报告必须连串口，演示与交付都不友好。
- **思路**：复用板级现成的 `configs/webpanel` 配置（thttpd +
  CGI `/data/www/cgi-bin` + libwebsockets + mDNS），做一个只读
  报告页：渲染 report.md 与 actions.log 最近 N 行，mDNS 广播
  域名便于局域网访问。只读、不设鉴权（局域网演示定位）。
- **依赖**：webpanel 配置现成；需评估 thttpd + websockets 的
  内存占用与 404KB 堆的相容性（可能与 PSRAM 项互相成全）。
- **工作量**：**2–3 人日**。

## 顺序建议

```
存储底座（8 SmartFS）──┬─→ M4 L3 热修复（1）─→ 签名校验（6）
                       ├─→ 黑匣子（4）
                       └─→ 网页报告（9）
PSRAM（2）─────────预算吃紧时补位（1/4/9）
通用心跳（3）／离线降级（5）／推送通知（7）──可随时并行
```

1 → 6 是主线（热修复闭环的完全体）；8 是横切底座，先做收益最大；
5 在网络条件差的演示场景里价值最高；3、7 各自独立、随时可插入。
